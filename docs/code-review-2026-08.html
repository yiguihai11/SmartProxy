P0 必须修 — 崩溃 / 安全 / 用户可感知失效

1. CA 根私钥入库且 embed 进二进制 安全

internal/admin/certs/admin_ca.key · embed_ca.go:13 · tls.go

问题：CN=SmartProxy Root CA、自签、CA:TRUE、有效期 20 年（2026→2046）的根 CA 私钥被 git 跟踪，并经 //go:embed 编进所有桌面/Android 二进制；/admin.crt 还引导用户把它装成系统信任根。已用 openssl 人工核实证书属性。

后果：任何拿到仓库或二进制的人都持有私钥，可为任意域名/IP 签发受信叶子证书，做全站 HTTPS MITM（解密面板凭据和流量）。

修法：轮换 CA；用 git filter-repo/BFG 从历史清除私钥；构建期注入而非入库；CA 证书可入库但私钥绝不入库；已安装旧 CA 的设备需撤销重装。

2. 断路器 Open 状态下节点永不恢复 正确性

internal/upstream/health.go:549-562

问题：recordSuccess 的 StateOpen 分支是空的；Open→HalfOpen 只能由 失败 触发（且冷却已过）。节点熔断后即使探测一直成功，状态也纹丝不动——要恢复反而得先再失败一次。

后果：IsAvailable() 对 Open 返回 false，默认/兜底选路与 UDP 路径（manager.go:198,356）永久跳过该节点，用户必须手动"一键恢复"或重启引擎——与故障转移目标相反。（注：规则路由路径 manager.go:293 仍会尝试连接 Open 节点，并非 100% 全部路径跳过。）

修法：冷却到期后下一次探测（无论成败）驱动 Open→HalfOpen；StateOpen 成功分支清零失败计数并转 HalfOpen/Closed，记录 latency。

3. 面板无鉴权时裸绑所有网卡 安全

internal/admin/admin.go:249-261, 141-143 · 注:config.go:457 是 SOCKS5 的 Listen.Host,面板地址硬编码于 admin.go:142

问题：authMiddleware 仅在 adminAuth != nil && Enabled && Username != "" 时校验；一旦鉴权未配置，TCP 监听（默认绑 [::] 全部接口）全部端点零鉴权开放。面板能写配置、改 ACL/chnroute、创建文件、切换电路。

后果：同 LAN（或端口转发暴露公网）者直接 PUT /config 写入恶意上游、篡改配置。

修法：未启用鉴权时拒绝绑通配地址（强制 loopback）或拒绝启动并显著告警；默认绑定改 loopback。

4. /files 三件套无目录沙箱 安全

internal/admin/admin.go:987-1140

问题：handleFiles/handleFileCreate/handleFileValidate 只做 filepath.Abs+Clean，从不校验路径是否在允许根目录内，也不检查符号链接。可 GET /files?path=/etc 列任意目录、把任意路径交给解析器（存在性/可读性 oracle）、在进程可写的任意位置建空文件（O_EXCL）。

修法：定义允许根（配置目录），用 filepath.Rel(base, abs) 校验越界；lstat 拒绝符号链接；create 限制在基础目录内。

5. 每次读 config 都无条件重写文件，触发 Go 热重载风暴 功能/性能

android/.../ConfigProvider.kt:35-53（getter 61-110）· MainActivity.kt:268,271,276-277,539-540 · PanelUrl.kt

问题：readConfig() 第一件事调 ensureConfig()，后者无条件 writeText(applyInvariants(...))，哪怕内容没改。首页每次 ON_RESUME 调 PanelUrl.url()（内部调 adminHttps()+adminPort()）与 adminAuth()（MainActivity.kt:276-277），回首页就重写 3 次；初次组合另加 ipv4/ipv6 getter（539-540），合计 5 次。

后果：每次写盘触发 fsnotify → configReload → UpstreamMgr.Reload() + DNS 静态记录重放，用户切回 App 可能断流；同时在主线程做磁盘写。

修法：读与 ensure（写）分离；getter 只读不写；ensure 仅启动/起 VPN 前调一次，写前比较 JSON 是否真的变化。

6. 重复/重投的 START intent 拆掉正在运行的 VPN 崩溃/状态

android/.../SmartProxyVpnService.kt:140-168 · mobile/bridge.go:39-42

问题：正常启动分支没有"已在运行就返回"的守卫。第二个 ACTION_START（快速双击、START_STICKY 系统重投、BOOT_COMPLETED 与 MY_PACKAGE_REPLACED 重叠）会再次 Builder.establish()（撤销第一个 TUN），然后 Go 侧返回 "router is already running"，失败分支执行 stopForeground+stopSelf 把运行中的服务收掉。

后果：正在跑的 VPN 被自己拆掉，UI 翻成未连接，留下 TUN 失效但引擎仍在跑的错乱窗口。

修法：正常分支开头加 if (startedEngine) return START_STICKY；start/restart 入口基于 isRunning 幂等。

7. TUN UDP WaitGroup Add/Wait 竞态可 panic 崩溃

internal/tun/handler.go:419-479

问题：tun.udpSend goroutine 经 safego.Go 启动但未纳入 remoteWg。主 select 退出后先 close 已有 remote、再 remoteWg.Wait()；此时 udpSend 可能正处于 getOrCreateRemote 慢路径（dial 最长 10s），dial 成功后 Add(1) —— 若 Wait 已在进行且计数为 0，触发 sync: WaitGroup misuse panic（被 safego recover 兜住，不崩进程）；若 Wait 已返回，新建的 remote conn 不在关闭清单，conn 与其 reader goroutine 永久泄漏（Add/Done 严格配对，不会出现 negative counter）。

修法：将 udpSend 纳入 WaitGroup（或第二个 Wg）并用 ctx/closeCh 通知停止；close 循环后用 ctx.Done() 保护慢路径不再 dial。

8. config.json 损坏即启动闪退、无法自愈 健壮性

android/.../ConfigProvider.kt:37-57 · SmartProxyApp.kt:14-15

问题：ensureConfig/readConfig 的 JSONObject(readText()) 与 writeText 无 try/catch；写入是 truncate+write 非原子，写一半被杀/磁盘满、面板写坏 JSON、并发读到中间态都会让 Application.onCreate 抛异常。

后果：App 一启动就闪退，且无法自愈（每次启动都读坏文件），等于"一次坏配置永久砖"。

修法：解析失败回退 assets 默认 config 并覆盖落盘；写入用临时文件 + rename 原子替换；onCreate 整体包 runCatching。

建议修复顺序

  1. 先堵安全/崩溃：CA 私钥轮换+移出仓库（#1，动作较大，需确认）、无鉴权禁止绑通配（#3）、files 沙箱（#4）、断路器恢复（#2）、重复启动自拆（#6）、UDP WaitGroup 竞态（#7）、坏 config 自愈（#8）。
  2. 再修泄漏/热重载正确性：Manager.Stop、移动端 udp_in_tcp、watcher 重绑、TUNHandler.ReloadConfig。
  3. 然后是 Android 主线程/ANR + config 读触发写（P0 #5）：改动面较大（IO 移出主线程、ensure 与 read 分离），但用户可感知收益最高。
  4. 最后滚动处理 P1/P2，并把 P3 仓库卫生顺手清掉。
